# 中文 → 日语软件测试用例翻译 Benchmark（100条）

> 用途：评估模型将中文软件测试用例翻译为日语的质量。重点覆盖操作、确认项目、期待结果三个组成部分，以及 UI、API、数据和业务规则等测试场景。

## 使用说明

- 将每条用例的「中文原文」单独输入待测模型；不要提供参考日语、语义判定规则或评分栏。
- 要求模型保留「操作」「确认项目」「期待结果」三个字段，并按原顺序输出日语。
- 保存模型原始输出，再依据判定规则评分。参考日语是基准表达，不是唯一正确译文。
- 允许合理的日语表达差异；重点检查测试步骤、对象、条件、数值、字段名、结果及否定关系是否一致。
- API 路径、JSON 字段名、枚举值、HTTP 状态码、ID、日期、金额、单位等技术信息原则上保持原样。
- 本 Benchmark 的日语采用自然、清晰、适合日本软件测试文档的表达。

## 单条评分规则（10分）

| 维度 | 分值 | 判定方法 |
|---|---:|---|
| 语义准确性 | 3 | 操作对象、确认对象、期待结果是否准确 |
| 信息完整性 | 2 | 步骤、条件、数值、字段、异常结果是否遗漏 |
| 技术术语准确性 | 2 | API、HTTP、request/response、字段名等是否正确 |
| 日语自然度 | 2 | 是否符合日本软件测试文档表达习惯 |
| 结构一致性 | 1 | 是否保留操作、确认项目、期待结果的结构 |
| **合计** | **10** | |

### 关键错误规则

- 关键错误包括：操作对象或动作错误；确认对象错误；期待结果反转；HTTP 状态码、数值、日期、金额、ID 错误；字段名或枚举值被改变；否定条件遗漏；API 应调用/不应调用关系颠倒；边界条件改变。
- 发生关键错误的单条最高 **4分**，即使日语流畅也不能评为合格。
- 轻微助词、语序、敬语差异不算关键错误；不要求逐字匹配参考译文。
- 不得把“API 不被调用”翻译成“API 调用失败”；不得把“未发现异常”强化为“没有异常”；不得把“可能”翻译成确定事实。

### 总体评价建议

| 指标 | 计算/判定方式 |
|---|---|
| 总分 | 100条得分之和，满分1000分 |
| 平均分 | 总分 ÷ 100 |
| 关键错误率 | 发生关键错误的题数 ÷ 100 × 100% |
| 合格率 | 单条得分≥8且无关键错误的题数 ÷ 100 × 100% |

| 单条结果 | 标准 |
|---|---|
| 优秀 | 9–10分，且无关键错误 |
| 合格 | 8分，且无关键错误 |
| 需改善 | 5–7分，或存在关键错误 |
| 不合格 | 0–4分 |

> 测试用例翻译不能只看日语是否自然。最重要的是日本测试人员能否依据译文正确执行测试，并依据期待结果准确判断 Pass / Fail。

## 使用建议

1. **分开统计场景**：分别统计认证、用户信息、列表检索、数据操作、文件、订单支付、权限、日期边界、异常处理和性能规则的得分。
2. **优先检查关键数据**：对 HTTP 状态码、ID、金额、日期、字段名和枚举值进行自动比对。
3. **检查可执行性**：日语译文应让测试人员明确知道执行什么操作、检查什么对象，以及什么结果才算通过。
4. **检查否定和条件**：尤其关注 API 不调用、数据不变、权限不足、条件成立时才执行等表达。
5. **控制比较变量**：比较不同模型或 Prompt 时，保持输入、模型参数、上下文长度和术语约定一致。
6. **人工复核关键错误**：对删除、支付、权限、数据更新及异常处理用例进行重点复核。
